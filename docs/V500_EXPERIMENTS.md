## V500-E1 — P1/P2a: exact tablebase and sound prover (TESTED)
- **Date:** 2026-11-11. `recur64-prove`: retrograde tablebase for KQvK / KRvK; AND/OR prover with ordering, width limit, node budget; independent proof checker; classical heuristic; symmetry-aware 80/10/10 split.
- **TESTED (7 tests, 0 failed):** KRvK longest mate 31 plies (16 moves) and KQvK 19 plies (10 moves) match the known maxima exactly; the tablebase agrees with the repo's independent forward `MateSolver` on thousands of positions (white and black to move, depth <= 3); full-width search stops at exactly the optimal depth and every proof passes the checker; width-limited proofs never fail the checker; the checker rejects a missing reply, a wrong first move and an illegal move; the split is symmetry-invariant.
- **Defect found and fixed during the build:** cozy-chess accepts adjacent kings and positions with the non-mover in check, which let a "capture the king" move into the enumeration; legality is now filtered explicitly (caught by the MateSolver cross-check test).

## V500-E4 — FAILED first learned attempt: value regression with piece-square tokens only (MEASURED, kept visible)
- **Date:** 2026-11-11, after E3 froze the gates and before any gated evaluation. Net v1: NNUE-style (384 piece-square tokens + 3 extras, h1 256, h2 32), MSE on `log2(1 + plies to mate)`, 40 epochs on TRAIN (CPU, 530 s), seed 5101, both materials. G0 parity held (Rust vs burn forward, max abs diff 1.4e-6).
- **Result:** validation MSE 0.119 (log2 units); exact optimal-move top-1 on TEST only about 0.3-0.5 for KRvK depths >= 8; in the prover on the VALIDATION split at width 2 (budget 1e5) it solved 0.40 / 0.20 / 0.05 / 0.05 / 0.00 at depths 9 / 10 / 11 / 12 / 13 against the classical width-2 baseline's 0.80 / 0.68 / 0.42 / 0.20 / 0.03 (TEST). It failed even shallow positions (depth 3: 0.85). This is not a gated result (VALIDATION, one seed); it is recorded because it changed the design.
- **Diagnosis (INFERRED, being tested by v2):** (1) regression of absolute distance does not discriminate siblings whose values differ by one or two plies; (2) piece-square sums cannot express relations (king distance, rook-king geometry).
- **Change (v2, a new logged design, thresholds untouched):** a LISTWISE RANKING loss over each parent's children (target uniform over the exactly optimal children, attacker minimises and defender maximises plies-to-mate) and king-relative displacement tokens (wK-bK, piece-bK, piece-wK, 15x15 grids each) added to the piece-square tokens, trained on the GPU. Same prover, same frozen gates.

## V500-E8 — P6 first KBNvK attempt FAILS the pre-registered rule on VALIDATION; a design bug found; extrapolation signal (MEASURED, kept visible)
- **KBNvK net (listwise ranking + king-relative tokens, h1 256 / h2 64, 1.22M sampled train parents of 20M, 20 epochs, seed 5101).** Exact-optimal top-1 on TEST by depth 0.47-0.84 (about 0.8 for depths >= 20) against 0.97 for KRvK; train top-1 0.891 vs validation 0.868, so the net is capacity-limited rather than overfit. (Wall time 6 h, mostly because the machine was shared with other jobs and slept.)
- **P6 pre-registered rule applied on VALIDATION (deep stratum depth >= 20, 10 per depth, budget 1e6, widths 1-4):** **0 of 140 solved at every width.** Width 1 fails in under a second; width 2 completes its search (mean 433k nodes, never exhausting the budget) with no proof, i.e. the net's top-2 contains no winning move somewhere in the tree; widths 3-4 exhaust the budget. P6-G1 (>= 0.5 on the deep stratum) is therefore NOT met by this net; TEST was not run on it (the frozen rule selects the width on VALIDATION first, and no width solved anything). Baselines on the same stratum: 0.000 for blind and every classical config (280 TEST positions, budget 1e6), deepest depth ever solved 14 of 33.
- **Design bug found while diagnosing (fixed, no result changed):** proof extraction unfolded the proof into a full TREE. Harmless for KRvK (the depth-16 tree has about 6.2e5 nodes) but astronomically large for deep KBNvK mates, and a perfect-oracle feasibility diagnostic grew to 46 GB and was killed (twice) while the system was low on memory. Proofs are now shared DAGs (`Arc`) with memoised extraction and memoised checking; the checker still uses only the rules, keyed by (position, proof node). Node counts are bit-identical before and after on 128 KRvK positions (493,593 nodes, same proofs); all 8 tests pass; the depth-16 KRvK proof is a 7,471-node DAG (6.19e5 unfolded).
- **EXTRAP signal (validation, seed 5101, width 2, budget 1e5; not yet the frozen G2):** an EXTRAP net (positions deeper than 8 moves withheld) solves 1.00 / 0.97 / 0.95 / 0.75 / 0.53 / 0.23 / 0.05 / 0.00 at depths 8-15. Competence extends a few moves beyond the training depth, then falls away; G2 as frozen (mean over depths 11-16 >= 0.395 and >= 0.75 x FULL) will be applied to the three EXTRAP nets on TEST.
- **Next (logged iteration, thresholds unchanged):** the oracle diagnostic (perfect ordering, width 1) bounds how many nodes this search structure needs for deep KBNvK; if the budget itself is unreachable the next step is a stronger net or a different search, not a lower threshold.
